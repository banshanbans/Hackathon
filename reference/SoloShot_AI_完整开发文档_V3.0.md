# SoloShot AI｜旅拍复刻教练完整开发文档

> **版本**：V3.0（一核双端 + Agent/Skill 端到端交付版）  
> **更新时间**：2026-07-16  
> **项目代号**：SoloShot AI  
> **赛道方向**：视觉搜索——视觉 + 语音，所见即所想  
> **正式交付形态**：共享 SoloShot Agent/Skill 核心 + 可公开访问的 H5 + 指定 iPhone 原生 App  
> **游园会主体验**：Apple 原生 iOS App 负责实时 Vision、AR 轮廓、语音和触觉陪拍  
> **赛前/远程体验**：H5 负责扫码即用、参考镜头圈选、方案生成、成片评价、分享与增长验证  
> **核心定位**：把用户在抖音中看到的旅行拍摄灵感，转换为一个人可以在现实场景中执行的拍摄任务；通过可复用 Agent/Skills 完成需求理解、视觉分析、方案生成、现实执行、结果判断和内容回流。

## 0. 文档摘要

SoloShot AI 不再被定义为单一客户端或一次性 Demo，而是一套能够被不同产品入口调用的**旅拍执行 Agent**。

整体采用“一核双端”结构：

```text
                    SoloShot Agent
               需求理解 / Skill Selection
                          │
       ┌──────────────────┼──────────────────┐
       ▼                  ▼                  ▼
Reference Understanding  Shooting Plan   Result Evaluation
参考镜头理解 Skill       拍摄方案 Skill    成片评价 Skill
       │                  │                  │
       ├──────────┬───────┴─────────┬────────┤
       ▼          ▼                 ▼        ▼
Scene Adaptation  Coaching Decision  Content Composer  Growth Analytics
灵感迁移 Skill     陪拍决策 Skill      内容生成 Skill      增长分析 Skill
                          │
                ┌─────────┴─────────┐
                ▼                   ▼
             H5 体验端          iOS 原生执行端
        低门槛体验/分享/增长     Vision/AR/语音/触觉
```

完整端到端链路：

```text
刷到抖音旅行视频
→ 暂停并圈选人物或画面
→ 点击“复刻这个镜头”
→ SoloShot Agent 理解需求并选择 Skills
→ 生成原图复刻或灵感迁移方案
→ 用户可在 H5 继续轻量体验，或生成任务二维码
→ iPhone 原生 App 读取同一任务
→ 本地 Vision + AR 轮廓 + 语音/触觉实时陪拍
→ 短视频录制与候选帧选择
→ Result Evaluation Skill 判断是否满足目标
→ 输出一条最高优先级纠正建议并二次拍摄
→ Content Composer Skill 生成 Before / After 竖屏内容
→ 发布“我的同款复刻”并回流抖音生态
```

V3.0 的关键升级：

1. 从“原生 iOS 单端”升级为“一核双端”，避免 App 分发限制影响赛前体验；
2. H5 和 iOS 不重复开发全部能力，而是按场景分工；
3. 核心业务沉淀为独立 Agent/Skills，能够被 H5、iOS、未来抖音小程序或创作者工具复用；
4. 按大区赛评分导向补齐端到端交付、AI 最小闭环、抖音生态放大、规模化增长和 ROI；
5. 游园会以原生 App 展示最强实时体验，同时用 H5 二维码证明可访问性、传播性和规模化潜力。

项目核心技术原则：

> **Agent 负责理解和编排，模型理解“怎么拍”，本地算法负责“陪用户拍”，双端共同完成增长和内容回流。**

# 1. 项目背景与机会

## 1.1 用户痛点

独自旅行用户常见问题：

1. 没有人帮忙取景，只能近距离怼脸自拍；
2. 网上摄影教程通常默认有摄影师，无法直接执行；
3. 用户携带行李、饮品时不方便打字操作；
4. 不知道如何利用道路、栏杆、长椅、建筑和自然光；
5. 即使使用三脚架，也不知道人物应该站在哪里；
6. 倒计时拍照难以完成走路、回头和转身等动态动作；
7. 拍完后没有人判断人物比例、位置和背景关系是否正确；
8. 抖音里收藏了大量旅拍内容，但真正到达现场时很少重新打开并完成复刻。

## 1.2 抖音平台机会

传统视觉搜索常在“识别并回答”后结束：

```text
看见内容 → 识别对象 → 返回信息
```

SoloShot AI 将链路延伸为：

```text
看见内容
→ 理解创意
→ 现实行动
→ 生成新内容
→ 回流平台
```

从抖音视角，项目能够同时创造以下价值：

- 提升旅行视频的消费深度；
- 将收藏转化为真实行动；
- 将观众转化为创作者；
- 为原作者带来更多复刻、@和互动；
- 产生新的竖屏内容供给；
- 形成模板、挑战和复刻链；
- 为 POI、生活服务和旅行内容建立后续连接。

# 2. 产品定位

## 2.1 一句话定位

> 用户在抖音圈选喜欢的旅行镜头后，SoloShot AI 将其转化为一个人可执行的现场拍摄任务，并通过原生 AR 轮廓和语音指导，陪用户拍出同款或完成灵感迁移。

## 2.2 本项目不是什么

本项目不是：

- 普通拍照姿势推荐器；
- 景点识别工具；
- 上传照片后生成一段泛化摄影教程；
- 通用美颜或修图应用；
- 单纯的人体姿势评分器；
- 只对固定素材运行的演示脚本；
- 与抖音内容生态无关的独立相机 App。

## 2.3 本项目是什么

本项目是：

- 抖音旅行内容的“现实执行层”；
- 单人旅行拍摄的实时 AI 教练；
- 从观看、圈选、复刻到发布的内容闭环；
- 将创作者镜头语言结构化为可复刻模板的系统；
- 在原图不适合当前环境时进行“灵感迁移”的拍摄助手。

## 2.4 核心差异化

### 差异一：从“建议”升级为“陪拍”

系统不是只告诉用户“可以站在三分线”，而是实时检测用户是否真的站到目标位置。

### 差异二：面向独自旅行

所有建议必须满足：

- 单人可以执行；
- 手机可以固定完成；
- 不依赖摄影师跟拍；
- 优先短视频选帧；
- 每轮只给一条可执行指令。

### 差异三：从抖音内容直接发起

主入口不是传统“上传图片”，而是：

```text
抖音视频暂停 → 圈选 → 复刻这个镜头
```

### 差异四：内容回流

最终结果不是只保存在相册，而是生成新的 9:16 复刻视频，并进入“发布我的同款复刻”。

# 3. 目标用户与角色

## 3.1 独自旅行用户

主要需求：

- 找到可单人完成的拍摄方式；
- 快速进入正确站位；
- 完成全身、半身或动态旅拍；
- 拍完后获得明确纠正；
- 生成可以发布的内容。

## 3.2 普通抖音内容消费者

主要需求：

- 看到喜欢的旅行视频后立即圈选；
- 保存为“旅拍任务”；
- 到达类似场景后执行；
- 查看其他人的复刻作品。

## 3.3 旅行创作者

主要需求：

- 将自己的视频转换为“可复刻模板”；
- 补充机位、动作和道具提示；
- 查看复刻次数和优秀作品；
- 获得新增曝光、互动和关注；
- 发起主题复刻挑战。

## 3.4 抖音平台

平台关注：

- 内容消费深度；
- 发起复刻率；
- 拍摄完成率；
- 同款发布率；
- 原作品回访和互动；
- 新内容供给；
- POI 与真实场景行动转化。

# 4. 项目目标与成功标准

## 4.1 产品目标

完成一个具备真实泛化能力、可以被评委直接体验、并能在指定 iPhone 上完成高质量现实执行的端到端产品：

1. 建立可独立调用的 SoloShot Agent 与核心 Skills；
2. H5 支持扫码即用、预设极速体验和自定义参考图；
3. 支持从抖音式视频页面暂停、截帧和圈选参考镜头；
4. 多模态模型能够分析人物、构图、机位、动作和场景意图；
5. 支持“原图复刻”和“灵感迁移”两种任务；
6. H5 能完成方案生成、轻量拍摄/上传、成片评价和分享；
7. H5 能创建跨端任务并由指定 iPhone 原生 App 继续；
8. iOS 原生相机显示 AR 人物轮廓，并通过 Vision 本地实时检测；
9. 系统指导用户调整左右、远近、完整入镜和简化姿势；
10. 自动录制短视频、选择候选帧并输出一条最高优先级建议；
11. 支持第二次拍摄并展示可见改善；
12. 生成真实的 Before / After 和 9:16 复刻内容；
13. 展示创作者模板、抖音内容回流和增长漏斗；
14. 记录 Agent 调用轨迹、成功率、延迟和单任务成本。

## 4.2 游园会展示目标

在 90 秒至 2 分钟内，让评委明确理解五件事：

1. 独自旅拍是一个真实且自然触发的场景；
2. 图片/视频圈选、语音约束和实时视觉检测具有不可替代性；
3. SoloShot Agent 能够选择并调用 Skills，完成从理解到满足判断的最小闭环；
4. H5 负责低门槛体验和规模化传播，iOS 负责原生实时陪拍；
5. 拍摄结果会转化为新的抖音内容，并带来用户、创作者和平台价值。

## 4.3 技术成功指标

- Agent JSON 合法率：≥ 98%；
- 核心 Skill 选择正确率：≥ 95%；
- H5 公开链接可用率：≥ 99%；
- H5 主流程成功率：≥ 95%；
- H5→iOS 任务接力成功率：≥ 95%；
- 指定 iPhone 启动成功率：100%；
- iOS 单次完整流程成功率：≥ 95%；
- 实时对齐反馈延迟：目标 ≤ 500 ms；
- 参考图动态分析：目标 ≤ 8 秒；
- 成片对比结果：目标 ≤ 8 秒；
- 本地核心拍摄能力在断网情况下仍可运行。

## 4.4 用户与业务成功指标

- 用户在 H5 前 15 秒内理解“圈选—复刻”；
- 用户进入 iOS 目标区域时间：≤ 20 秒；
- 第二次成片可见改善率：目标 ≥ 80%；
- 每轮只输出一条可执行建议；
- 评委可在不安装 App 的情况下验证核心 AI 闭环；
- 至少形成一条可统计的“内容曝光—任务生成—拍摄—分享/发布”漏斗；
- 单任务模型、媒体和存储成本可被统计；
- 创作者模板能够带来可归因的复刻任务和新内容。

# 7. 一核双端交付策略

## 7.1 总体原则

采用：

> **一个共享 Agent/Skill 核心、两个能力互补的客户端。**

不采用：

- H5 和 iOS 各写一套完整业务逻辑；
- 两端分别维护 Prompt 和数据结构；
- 为追求“功能对齐”而把实时 Vision 强行搬进 H5；
- 只做宣传 H5，无法完成真实 AI 链路；
- 只做原生 App，导致评委无法提前扫码体验和传播。

## 7.2 H5 的产品定位

H5 是：

- 赛前评委体验入口；
- 游园会扫码体验入口；
- 抖音内容承接页；
- 获客、分享、增长和数据验证入口；
- 低设备门槛的端到端轻量版本。

H5 必须真实跑通：

```text
选择/上传参考图或视频帧
→ 圈选人物
→ Agent 分析
→ 生成拍摄方案
→ 展示静态目标轮廓
→ 上传或拍摄成片
→ AI 评价与纠偏
→ 生成分享卡/任务二维码
```

H5 不强求首版实现：

- 高频人体关键点跟踪；
- 原生级自动曝光与视频控制；
- 复杂触觉反馈；
- 与 iOS 相同精度的实时动作指导。

## 7.3 iOS 的产品定位

iOS App 是：

- 游园会主体验端；
- 真实拍摄执行端；
- 原生设备能力增强端；
- 弱网下仍可工作的本地陪拍端。

重点能力：

- AVFoundation 后置相机；
- Vision 本地人体检测；
- 原生 2D AR Overlay；
- 实时左右、远近、完整入镜和简化姿势判断；
- 语音与触觉反馈；
- 自动倒计时和视频录制；
- 本地候选帧；
- 任务二维码导入。

## 7.4 分发策略

- 游园会指定 iPhone：通过 Xcode 开发签名或 Ad Hoc 安装冻结版本，不依赖 App Store 审核；
- 普通评委和远程用户：直接访问 H5，不要求安装；
- TestFlight：只作为已安排测试人员的补充渠道，不作为现场扫码主路径；
- App Clip：作为后续产品化方向，不纳入首版必需范围。

## 7.5 双端共享与独有能力

| 能力 | H5 | iOS | 共享 Agent/后端 |
|---|---|---|---|

# 9. 两种拍摄模式

## 9.1 原图复刻

目标：尽量还原参考画面。

提取并匹配：

- 人物归一化位置；
- 人物占画面比例；
- 头顶空间；
- 脚部基线；
- 身体朝向；
- 动作类型；
- 相机高度；
- 相机俯仰；
- 背景主体关系；
- 动态动作时机。

适用场景：

- 当前场景与原图相似；
- 用户希望精准“拍同款”；
- 建筑、道路或栏杆结构相近。

## 9.2 灵感迁移

目标：保留镜头语言，不机械复制坐标。

示例：

```text
参考图意图：低机位、人物右侧、道路纵深、行走回头
当前场景：没有道路，但存在栏杆和建筑透视线
输出方案：沿栏杆方向行走，人物仍位于右侧三分线，保留低机位和回头动作
```

适用场景：

- 原图与现场背景差异较大；
- 当前环境无法复刻原机位；
- 用户只想保留氛围、动作和构图逻辑。

# 12. SoloShot Agent 与 Skill 设计

## 12.1 主 Agent：SoloShot Coach Agent

职责：

- 理解用户目标：复刻、灵感迁移、评价、继续拍摄或生成内容；
- 识别输入类型：图片、视频帧、文本、语音、现场照片；
- 选择并编排 Skills；
- 管理会话状态和多轮拍摄；
- 判断结果是否满足目标；
- 在 Skill 失败或置信度不足时触发澄清、手动圈选或规则降级；
- 记录调用轨迹，供评委和开发者查看。

## 12.2 Skill 选择示例

```text
用户上传参考图并说“尽量拍同款”
→ Reference Understanding
→ Shooting Plan

用户上传参考图 + 现场图并说“这里没有草原”
→ Reference Understanding
→ Scene Adaptation
→ Shooting Plan

用户上传刚拍的照片
→ Result Evaluation
→ Coaching Decision

用户确认满意并准备分享
→ Content Composer
→ Growth Analytics
```

## 12.3 Reference Understanding Skill

输入：

- 参考图片或视频帧；
- 用户圈选区域；
- 可选文本/语音约束。

输出：

- 人物框和中心；
- 人物比例；
- 构图关系；
- 相机高度、角度和镜头建议；
- 动作和朝向；
- 背景主体；
- 镜头语言和场景意图；
- 风险与不可复刻项；
- 置信度。

## 12.4 Shooting Plan Skill

将分析结果转成一个人可以执行的方案：

- 手机支撑和摆放方式；
- 人物目标位置与比例；
- 推荐拍摄距离；
- 动作脚本；
- 倒计时或视频模式；
- 是否需要行李、饮品等道具；
- 安全和环境限制；
- H5 轻量执行方式；
- iOS 增强执行参数。

## 12.5 Scene Adaptation Skill

负责“灵感迁移”：

- 判断现场是否能直接复刻；
- 提取可保留的镜头语言；
- 寻找道路、栏杆、建筑、树木等替代结构；
- 重算人物位置和背景关系；
- 返回调整理由和可执行方案。

## 12.6 Result Evaluation Skill

输入参考镜头、ShotPlan 与成片，输出：

- 人物位置和比例差异；
- 完整入镜；
- 姿势和朝向；
- 背景遮挡；
- 镜头意图保留程度；
- 最高优先级问题；
- 是否需要重拍；
- 是否达到发布阈值。

## 12.7 Coaching Decision Skill

将检测和评价转成受控指令：

```text
no_person
move_left
move_right
move_forward
move_backward
feet_outside
adjust_camera
turn_body
ready_to_capture
```

实时 iOS 指令主要由本地规则执行，但使用同一标签和 Schema，保证与后端评价一致。

## 12.8 Content Composer Skill

负责：

- Before / After 卡片；
- 9:16 复刻视频脚本和合成参数；
- 标题、话题和发布文案；
- 原作者/模板来源；
- 分享链接、任务卡和二维码；
- 隐私确认与发布前预览。

## 12.9 Growth Analytics Skill

负责把产品行为转成可分析事件：

- 渠道来源；
- 圈选与复刻点击；
- Agent 成功率；
- H5 到 iOS 接力；
- 拍摄完成和重拍；
- 内容生成、分享和发布；
- 单次任务模型成本；
- 模板传播系数。

## 12.10 Skill 工程规范

每个 Skill 必须具备：

- 明确的输入/输出 Schema；
- 版本号；
- 超时和重试策略；
- 置信度；
- 可观测日志；
- 独立测试集；
- 降级实现；
- 业务指标；
- 可从 H5、iOS 或未来平台入口独立调用。

## 12.11 Agent 调用轨迹展示

比赛现场可展示开发者面板：

- 主流 iOS Safari、Android Chrome 和桌面 Chrome 可用；
- 弱网下展示缓存的预设流程；
- 所有关键失败均有明确恢复入口。

## 14.1 AppState 与状态机

建议核心状态：

```swift
enum AppFlowState {
    case launch

    case referenceAnalyzing
    case modeSelection
```

原则：

- 页面不直接散落管理状态；
- 所有异步任务通过统一状态机切换；
- 每个状态有明确进入条件和失败出口；
- 支持拍摄流程中断后恢复；
- 第二次拍摄保留第一次结果和建议。

## 14.2 Camera Engine

职责：

- 请求相机权限；
- 初始化 `AVCaptureSession`；
- 固定后置主摄 1×；
- 输出实时 `CMSampleBuffer`；
- 管理相机方向；
- 锁定或调整曝光和对焦；
- 视频录制；
- 录制状态回调；
- 前后台恢复；
- 释放相机资源。

建议：

- 相机 Session 在后台串行队列运行；
- Vision 不处理每一帧；
- UI 更新回到主线程；
- 固定竖屏以降低坐标映射复杂度。

## 14.3 Vision Engine

职责：

- 人体关键点检测；
- 人体边界框计算；
- 置信度过滤；
- 多人时选择主要人物；
- 完整入镜判断；
- 身体方向估计；
- 简化姿势特征提取。

主要关键点：

- 头部；
- 左右肩；
- 左右肘；
- 左右腕；
- 左右髋；
- 左右膝；
- 左右踝。

多人策略：

1. 优先选择与目标轮廓交叠最大的完整人物；
2. 若多人置信度接近，提示“画面中有多个人，请只保留拍摄者”；
3. 工作人员模式允许手动锁定主体。

## 14.4 Overlay Renderer

职责：

- 半透明目标人物轮廓；
- 头部目标圆；
- 肩部参考线；
- 身体中心线；
- 脚底基线；
- 方向箭头；
- 对齐进度；
- 倒计时；
- 录制状态；
- 成功动画。

视觉建议：

- 未检测到人物：轮廓虚线；
- 检测到人物：显示轻量状态；
- 接近目标：轮廓逐渐填充；
- 完全对齐：成功动画和触觉反馈；
- 不显示过多调试骨架，避免像工程工具。

## 14.5 Alignment Engine

职责：

- 比较目标人物与当前人物；
- 生成单条最高优先级指令；
- 防止左右抖动；
- 控制语音频率；
- 判断是否可以开始拍摄。

状态枚举：

```swift
enum AlignmentInstruction {
    case noPerson
    case multiplePeople
    case moveLeft
    case moveRight
    case moveForward
    case moveBackward
    case feetOutside
    case headOutside
    case adjustBodyDirection
    case adjustArm
    case holdStill
    case ready
}
```

优先级：

```text
没有人物
> 多人干扰
> 人物未完整入镜
> 人物大小
> 左右位置
> 姿势
> 稳定保持
> 已对齐
```

防抖机制：

- 同一结果连续 3 帧以上才确认；
- 同一语音指令至少间隔 2 秒；
- 设置进入阈值和退出阈值，形成迟滞区；
- 相邻指令冲突时优先保持上一条；
- `ready` 状态需持续 1–1.5 秒。

## 14.6 Voice & Haptics

语音原则：

- 每次只播一句；
- 不使用复杂摄影术语；
- 句子控制在 4–12 个字；
- 同一指令不连续重复；
- 倒计时语音与动作脚本协调。

触觉反馈：

- 检测到人物：轻反馈；
- 构图对齐：成功反馈；
- 开始录制：明确反馈；
- 拍摄结束：完成反馈；
- 错误：警告反馈。

## 14.7 Capture Engine

职责：

- 5–8 秒短视频录制；
- 动作脚本定时；
- 视频本地保存；
- 候选帧提取；
- 关键帧元数据记录；
- 支持单张照片降级。

录制推荐流程：

```text
进入 ready
→ 语音说明动作
→ 3 秒倒计时
→ 开始录制
→ 第 1–6 秒播放动作节奏提示
→ 自动结束
→ 本地抽帧
```

## 14.8 Frame Selection Engine

候选帧评分：

```text
总分 =
人物完整度 × 25%
+ 人物位置匹配 × 20%
+ 人物比例匹配 × 15%
+ 姿势匹配 × 15%
+ 清晰度 × 15%
+ 面部可用性 × 10%
```

首版可先实现：

- 完整入镜；
- 人物位置；
- 人物比例；
- 清晰度；
- 简化姿势。

保留用户手动选择，AI 推荐不应强制替用户决定。

## 14.9 Result Composer

职责：

- 参考图、第一次和第二次成片排版；
- 生成 9:16 竖屏视频；
- 添加 AI 建议动画；
- 生成话题和描述；
- 进入发布预览。

建议视频结构：

```text
参考镜头 1 秒
→ 第一次成片 1.5 秒
→ AI 建议 1 秒
→ 第二次成片 2 秒
→ “一个人也能拍同款” 1 秒
```

# 15. 为什么采用原生 2D AR，而非首版复杂三维 AR

## 15.1 目标场景

比赛主要场景：

- 手机固定在支架上；
- 使用后置主摄 1×；
- 用户站在数米外；
- 相机视角基本不移动；
- 轮廓用于指导屏幕中的人物位置和比例。

## 15.2 推荐实现

```text
AVCaptureVideoPreviewLayer
+ 原生 Overlay Layer
+ Vision 当前人物关键点
+ 归一化目标坐标
```

目标轮廓固定在屏幕坐标系，而不是锚定在真实世界坐标中。

优点：

- 开发风险低；
- 性能稳定；
- 坐标关系容易控制；
- 适合固定机位；
- 视觉效果足够强；
- 可快速实现人物框、轮廓、头部区和脚底线。

## 15.3 后续使用 ARKit 的场景

满足以下需求时再加入 ARKit/RealityKit：

- 手机允许移动；
- 轮廓需要固定在真实地面位置；
- 需要提示手机应摆放的空间位置；
- 需要检测地面、墙面和真实尺度；
- 需要三维虚拟人物示范动作；
- 手机移动后虚拟人物仍保持原位。

# 16. AI、本地算法与产品规则分工

## 16.1 确定性本地算法负责

- 当前人物检测；
- 人物中心与边界；
- 完整入镜；
- 左右、远近；
- 关键点角度；

- 指令优先级；
- 指令防抖；

## 16.2 多模态模型负责

- 参考图人物区域理解；
- 构图意图；
- 机位高度和角度；
- 动作语义；
- 背景主体；

示例：

- 使用不可执行的摄影术语；
- 主观评价外貌；
- 延迟过高；
- 同时给出多条建议。

# 18. AR 轮廓与姿势映射

## 18.1 基础目标布局

```swift
struct TargetLayout: Codable {
    let centerX: CGFloat
    let centerY: CGFloat
    let width: CGFloat
    let height: CGFloat
    let headPoint: CGPoint
    let footLineY: CGFloat
    let bodyDirection: BodyDirection
    let poseTemplate: PoseTemplate?
}
```

所有坐标采用 0–1 归一化，映射到 `AVCaptureVideoPreviewLayer` 的实际显示区域。

## 18.2 目标轮廓来源

按优先级：

1. 根据人物框生成标准化人体轮廓；
2. 根据参考图关键点生成简化骨架；
3. 使用动作模板 SVG；
4. 预设模板缓存；
5. 固定人物框降级。

## 18.3 实时对齐计算

```text
横向误差 = 当前中心 X - 目标中心 X
比例误差 = 当前人物高度 - 目标人物高度
完整度 = 当前边界是否超出画面
姿势误差 = 关键点角度与目标模板差异
```

初始阈值建议：

```text
横向误差 < 6%：通过
6%–12%：轻微移动
> 12%：明确移动

高度误差 < 10%：通过
10%–18%：轻微前后调整
> 18%：明显前后调整
```

最终阈值以线下实测为准。

## 18.4 简化姿势匹配

首版只判断高价值特征：

- 身体正面、侧身或背向；
- 肩膀方向；
- 是否抬手；
- 是否回头；
- 是否站立；
- 是否正在行走；
- 双脚是否分开；
- 行李箱或饮品作为动作提示，不要求精确检测。

# 23. 隐私、安全、版权与内容合规

## 23.1 用户影像

- 实时人体检测优先在设备本地运行；
- 不进行身份识别；
- 不建立人脸档案；
- 临时视频完成处理后可自动删除；
- 用户可手动删除所有会话内容；
- 未经明确确认不上传和发布；
- 结果页必须提供发布预览。

## 23.2 参考内容

- 参考视频只用于构图与动作分析；
- 不生成去水印搬运内容；
- 结果中保留原作者或参考来源概念；
- 用户发布前可查看最终生成内容；
- 模板必须避免直接复制受限内容资产。

## 23.3 用户表达

系统不得：

- 主动评价身材；
- 使用羞辱性语言；
- 对外貌进行审美打分；
- 推荐危险站位；
- 推荐进入车道、悬崖、轨道或禁止区域；
- 鼓励阻塞公共通道。

## 23.4 安全规则

若检测到高风险环境或用户主动输入相关限制，提示：

- 保持远离车辆和道路；
- 不要在栏杆外侧拍摄；
- 不要在拥挤通道架设设备；
- 优先选择稳定手机支撑；
- 夜间避免独自在偏僻位置拍摄。

# 27. 容灾与降级

## 27.1 总体降级层级

```text
正常模式：真实分析与完整功能
    ↓ 失败
一级降级：缓存最近一次成功结果
    ↓ 失败
二级降级：规则模板继续拍摄
    ↓ 失败
三级降级：手动人物框与工作人员控制
    ↓ 失败
四级降级：备用真实录制演示视频
```

## 27.2 模型超时

- 使用预设参考图缓存；
- 使用已解析的参考模板；
- 允许用户手动调整人物框；
- 进入本地规则拍摄。

## 27.3 Vision 检测失败

- 降低分析频率并重试；
- 提示移动到更亮区域；
- 使用人物边界检测替代关键点；
- 允许工作人员点击“已就位”。

## 27.4 视频录制失败

- 自动切换单张照片；
- 仍完成成片比较；
- 结果页标记当前为照片模式。

## 27.5 语音失败

- 使用大字号文字；
- 使用箭头动画；
- 使用触觉提示；
- 工作人员口头辅助。

## 27.6 网络失败

本地仍可运行：

- 相机；
- 人体检测；
- AR 轮廓；
- 左右、远近；
- 倒计时；
- 视频录制；
- 本地候选帧。

在线功能降级：

- 使用缓存参考分析；
- 使用本地规则生成纠偏；
- 稍后再生成发布视频。


# 30. 风险清单与应对

## 30.1 双端范围风险

风险：H5 和 iOS 追求功能完全一致，导致开发量翻倍。

应对：

- 共享 Agent、Schema 和业务状态；
- H5 负责轻量体验和增长；
- iOS 负责实时设备能力；
- 每个功能先确认属于共享、H5 独有还是 iOS 独有；
- 不以双端 UI 一致作为验收目标。

## 30.2 Agent 形式化风险

风险：只把普通接口改名为 Skill，评委看不到真实编排价值。

应对：

- 展示意图识别和不同 Skill 选择；
- 支持原图复刻、灵感迁移、成片评价等不同路径；
- 每个 Skill 有 Schema、版本、日志和独立测试；
- 展示失败时的澄清或降级。

## 30.3 H5 风险

- 内置浏览器权限限制；
- 视频编码兼容；
- 页面被系统回收；
- 大文件上传慢；
- 网页相机效果弱。

应对：

- H5 核心闭环允许文件上传；
- 相机是增强功能，不是唯一入口；
- 图片压缩和分片上传；
- session 恢复；
- 明确推荐浏览器；
- 预设极速体验缓存。

## 30.4 iOS 技术风险

- Vision 弱光和远距离不稳定；
- 坐标映射错误；
- 高频推理发热；
- 视频录制与检测资源竞争；
- 任务数据版本不一致。

应对：

- 降低推理帧率；
- 固定设备、镜头和方向；
- 连续帧确认与迟滞；
- 本地缓存 TargetLayout；
- 版本化 Schema；
- 手动“已就位”兜底。

## 30.5 产品风险

- 被理解为普通姿势推荐；
- 多模态显得堆功能；
- 灵感迁移解释不清；
- 第二次改善不明显；
- 内容发布只是概念页面。

应对：

- 前 10 秒展示 Before / After；
- 强调“现实执行”和“满足判断”；
- 每种模态对应明确必要性；
- 选择可明显改善的主场景；
- Content Composer 真实生成竖屏结果文件。

## 30.6 增长风险

- 用户只体验一次；
- 达人不愿制作模板；
- 模板质量参差；
- 分享卡传播弱；
- 模型成本高于内容价值。

应对：

- 任务夹、挑战和连续创作；
- 自动生成模板，降低达人负担；
- 模板质量评分和审核；
- 分享卡直接带“我也要复刻”；
- 缓存、按需 Skill 和本地计算降低成本。

## 30.7 展示风险

- 展位多人误入；
- 语音听不清；
- 手机过热；
- 网络不稳定；
- H5 二维码打不开；
- 原生 App 崩溃。

应对：

- 安全区和工作人员引导；
- 文字、语音、触觉三重提示；
- 主备设备和散热；
- 独立热点；
- H5 静态备用域名/二维码；
- 多级降级和预录视频。

# 34. 最终开发原则

1. 从抖音内容开始，以现实拍摄和内容回流结束；
2. 采用“一核双端”，而不是两套重复产品；
3. H5 负责低门槛体验、传播、增长和赛前评审；
4. iOS 负责 Vision、AR、语音、触觉和高质量现场执行；
5. Agent 负责需求理解、Skill Selection、状态管理和满足判断；
6. 核心能力必须沉淀为有 Schema、版本、日志和降级的 Skills；
7. 模型理解“怎么拍”，本地算法负责“陪用户拍”；
8. 首版原生 AR 采用 AVFoundation + Vision + 2D Overlay；
9. 三维 ARKit 是增强能力，不作为主流程依赖；
10. H5 必须是真实产品闭环，不是宣传页；
11. 自定义参考图必须真实运行，预设数据只用于缓存和容灾；
12. 保留原图复刻和灵感迁移两种模式；
13. 每次只给一条最高优先级建议；
14. 所有指令必须单人可执行、具体、安全；
15. 实时语音不由大模型自由生成；
16. 任何自动推荐都保留手动选择和恢复入口；
17. H5 和 iOS 必须围绕同一 SoloShotSession 接力；
18. 每个核心功能同时定义技术指标、用户指标和成本指标；
19. 在第一阶段就跑通 API 级最小闭环，在早期完成双端接力；
20. 主分支始终保持可演示，不在最后集中联调；
21. 线下阶段重点调整环境、阈值、话术和稳定性；
22. Demo 前 10 秒先证明结果，随后展示 Agent 链路；
23. 评委必须看到真实场景、多模态必要性、抖音生态和增长逻辑；
24. 不夸大未验证的 ROI，所有规模化结论绑定可测指标；
25. 最终目标不是“分析得专业”，而是让用户第二张照片明显优于第一张，并愿意发布新的抖音内容。

# 35. 项目最终表达

## 35.1 面向用户

> 一个人旅行，也可以把刷到的镜头真正拍出来。

## 35.2 面向创作者

> 让每一条优质旅行视频，都能变成观众可以参与的可复刻模板。

## 35.3 面向抖音平台

> 把旅行内容从“被观看和收藏”，升级为“被理解、被执行、被再次创作”，并通过 H5、原生体验和 Agent/Skill 形成可复用、可增长的产品能力。

## 35.4 面向技术评委

> SoloShot AI 不是把多个模型接口串在一起，而是通过主 Agent 理解意图和选择 Skills，由视觉理解、场景迁移、拍摄方案、结果判断和内容生成共同构成可观测、可复用、可降级的最小业务闭环。

## 35.5 路演结束语

> SoloShot AI 理解抖音里的镜头创意，把它变成一项可执行的旅拍任务；H5 让任何人都能低门槛发起和分享，原生 iPhone 则在真实现场用视觉、AR 和语音陪用户把照片拍出来。完成之后，这次行动又会成为一条新的抖音内容。
